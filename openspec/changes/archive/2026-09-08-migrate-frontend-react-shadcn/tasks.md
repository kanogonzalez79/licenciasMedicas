## 6. Pipeline de build y limpieza

- [x] 6.1 Agregar el target de MSBuild en `Web.csproj` que corre `npm ci && npm run build` sobre `Web.Client` y embebe `dist/` (mecanismo confirmado en el paso 1), gateado para no correr en `dotnet build` de Debug; verificar con `dotnet publish` que el `.exe` resultante sirve la nueva SPA sin tener `Web.Client/node_modules` presente al momento de ejecutar el `.exe`. **Incluye** `app.MapFallbackToFile("index.html", ...)` en `Program.cs`.

  **Bug real encontrado y corregido**: `%(RecursiveDir)`/`%(Filename)`/`%(Extension)` (las mismas que funcionaron en el spike de la tarea 1.1) NO se calculan para items creados dentro de un `<Target>` — solo funcionan en `ItemGroup` estáticos evaluados al cargar el proyecto. Con ellas, **todos** los archivos del `dist/` colapsaban al mismo `Link="wwwroot\"`, y `GenerateEmbeddedResourcesManifest` fallaba con `System.InvalidOperationException: An item with the name '' already exists`. Corregido armando el `Link` con `$([System.IO.Path]::GetRelativePath(...))` sobre `%(FullPath)` en vez de depender de `RecursiveDir`. El spike de la tarea 1.1 "funcionó" porque ahí el `ItemGroup` era estático (a nivel de proyecto, no dentro de un `Target`) — no validaba este caso.

  **Segundo bug real encontrado y corregido**: con `wwwroot` vacío en Debug (nada se embebe salvo en Release), `ManifestEmbeddedFileProvider` explotaba al arrancar (`Could not load the embedded file manifest`) porque el manifiesto ni se genera sin `EmbeddedResource` items. Corregido envolviendo `UseDefaultFiles`/`UseStaticFiles`/`MapFallbackToFile` (y el auto-open del navegador) en `if (!app.Environment.IsDevelopment())` — en dev el backend no necesita servir `wwwroot` en absoluto, porque quien sirve el frontend es `vite dev` (tarea 6.2).

  Verificado de punta a punta: `dotnet publish -c Release` a una carpeta aislada (sin acceso a `Web.Client`/`node_modules`) → la carpeta publicada no tiene rastro de Node/JS, el `.exe` corrido desde ahí sirve `<title>Licencias Médicas</title>`, `/unidades` (ruta sin archivo físico) responde 200 vía el fallback, y `/api/unidades` sigue funcionando (no capturado por el fallback). De paso se corrigió el `<title>` (quedaba el placeholder `licenciasmedicas-web-client` de Vite) y se eliminaron sobrantes sin uso del scaffold (`App.css`, `assets/hero.png`, `assets/react.svg`, `assets/vite.svg`, `public/icons.svg`).

- [x] 6.2 Configurar `vite dev` con proxy de `/api/*` hacia un puerto fijo de desarrollo del backend (sin afectar el puerto efímero de producción); verificar que `npm run dev` + `dotnet run` permiten navegar la app con HMR y que las llamadas a `/api/*` responden. `Program.cs` ahora elige el puerto según `IsDevelopment()`: fijo (`5244`, el mismo que ya traía el `launchSettings.json` del scaffold pero que estaba siendo ignorado) en dev, efímero en producción — sin tocar el comportamiento de producción. `vite.config.ts` apunta su proxy a ese mismo puerto fijo.
